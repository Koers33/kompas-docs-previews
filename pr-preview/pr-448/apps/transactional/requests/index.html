Requests app

Requests is where client requests are captured, sent and tracked. Every request gets a Request Number when it is created, and carries its Request Type, Request Status, Client, Counter Party, amounts, currencies and dates.

What is this app for?

A request is the formal ask that treasury answers with terms. The Request Type decides what kind of answer it expects: an Indication Rate, a Call Rate, an Order, a Quotation or an Internal Contract. The object page shows only the section for the type you chose, together with the rows of the response that comes back for it.

The request also records who it is for and what it is about — client, optional project, references, currency pair, transaction side and value dates — so the same record carries the ask and the answer through to completion.

When should I use this app?

Use it to raise a request for a client, to send it to treasury, to check where a request stands, to duplicate one you have already written, and to see whether it has been answered.

A request can also be raised from a project item in Project Items: run Create Request there and choose the request type. The answers are read in Internal Contracts and Internal Responses; the full sequence is described in the Client Workflows Guide.

Who can access this app?

The app is reached through portal access plus the roles your administrator has assigned you — see Roles and Access. No narrower launchpad audience is recorded for it, so it is treated as available to anyone with portal access.

The records behind the screen are scoped: the Treasury role has full use of requests, including Send Request and Duplicate Request. A user holding the Client role gets the same use only for a client business partner they are actively linked to as a Request Author, and read-only access when that link is a Request Viewer. Client users therefore see a narrower set of requests than treasury users do.

How does work progress in this app?

  1. Create a request: choose the client and the Request Type, then complete the details that type asks for. The Request Number is assigned for you on creation.
  2. Choose a Project if the request belongs to one. The project-linked details — client reference, item reference, document number and country — appear once a project is selected.
  3. Tick Finalised when the details are complete. A request marked finalised can no longer be edited.
  4. Run Send Request. The status moves from Open to Requested, and a cost provision entry is raised against the send.
  5. The response is recorded against the request in its type’s section, and the client’s authorisers and response viewers are notified where their contact details are recorded. The Unanswered Requests view is how you find requests still waiting for an answer.
  6. Duplicate Request starts a fresh unsaved copy of a saved request, for when you want the same ask again with different details. It also raises a cost provision entry.

Status is carried on the record and colour-coded in the list: Open, Requested, Await Approval and Closed.

What can change what I see or do?

  • Request Type decides the screen. Only the section for your type is shown, and each type has its own required details — a save is refused with a message naming every value that is still missing.
  • Send Request is offered only on a saved request that is still Open and already ticked Finalised. Anything else offers nothing to send.
  • Finalised locks the record. Once it is ticked the request can no longer be edited, so correct the details before you finalise.
  • Transaction Side decides which amount you enter: the buy amount appears for a buy, the sell amount for a sell, and the record’s amount is taken from the side you chose.
  • The currency pair is worked out for you from the buy and sell currencies and stays read-only. A combination with no configured pair is refused when you save, with a message naming the pair.
  • Optional Start Date is only offered when the FEC Type is Partially Optional.
  • Call Rate and Order requests get an expiry date 30 days after the start date when you do not enter one yourself.
  • Contract rows are treasury’s to add. A client user cannot create them, and treasury can only add them once the request is finalised, requested, and the client permits internal contracts.
  • The view you select decides what is listed — ready-made views narrow the list to open, requested or unanswered requests, or to a single request type.

Where can I review the results?

Start with the list: Request Number, Request Type and the colour-coded Request Status tell you where each request stands, and the ready-made views narrow it further. Open a request and read its type section for the response rows, its references, and its Finalised flag.

The response itself is read in Internal Contracts or Internal Responses, and the cost raised by sending or duplicating a request appears in Cost Provisions.

What should I check if I can’t continue?

  • A save is refused naming missing values: complete the details your request type requires and save again.
  • “The Currency Pair … is not available”: choose a buy and sell currency for which the platform has a configured pair, or ask your administrator to add it.
  • Send Request is not offered: the request is not saved, not Open, or not yet ticked Finalised.
  • You cannot edit a request: it is already finalised, or your link to the client is read-only — see Roles and Access.
  • A request you expect is missing: check which view is selected before assuming it was lost.

Which task guides are available?

No task guide is published for this app yet; raising, sending, duplicating and tracking a request are covered on this page, and the end-to-end sequence is in the Client Workflows Guide. Read Using the Fiori Apps once for how drafts, value helps and save behaviour work across the platform.

What should I do next?

Read the answer in Internal Contracts or Internal Responses, follow any payment that comes out of it in Payment Requests, and keep the project the request belongs to up to date in Projects.
