Business Partners Testing Guide

This guide walks you through testing the Business Partners app on the live BTP Cloud Foundry deployment, covering:

  1. Creating an Organization Business Partner with all sub-records
  2. Creating Natural Person BPs for contact people
  3. Linking Business Partners with relationships and testing authorization

FLOW 1 — Create an Organization Business Partner

App: Business Partners (Work Zone tile)
Role needed: Treasury
Under test: Create org BP, populate addresses/banks/emails/phones, set client flags, KYC/AML, SSI

Step 1.1 — Open the Business Partners App

From the Work Zone launchpad, click the Business Partners tile. You will see a List Report with a searchable table of all business partners.

Step 1.2 — Click Create

Click the Create button in the toolbar. A new draft Business Partner opens on the Object Page.

FLOW 2 — Create Natural Person BPs for Contact People

App: Business Partners
Role needed: Treasury

Before linking, you need individual Natural Person records. Create them now.

Step 2.1 — Create Natural Person BPs

Repeat these steps for at least 3 contact people:

  1. From the Business Partners List Report, click Create
  2. Set Business Partner Category = Natural Person (code 02)
  3. Fill in:
    • First Name: e.g., John
    • Last Name: e.g., Smith
  4. In the Emails table, add: john.smith@acme.co.za (type: Work)
  5. Save

Create at minimum these people (adjust names as needed):

RoleExample NameEmail
CEOJohn Smithjohn.smith@acme.co.za
CFOJane Doejane.doe@acme.co.za
Compliance Off.Alice Brownalice.brown@acme.co.za
TraderBob Traderbob.trader@acme.co.za
Client AdminCarol Admincarol.admin@acme.co.za

Important: These Natural Person BPs are for users who already have IAS accounts and have been claimed/onboarded in Flow 1. The BP ID should match the IAS user ID so that the relationship grants real authorization.

FLOW 3 — Link Business Partners with Relationships

App: Business Partners
Role needed: Treasury
Under test: Business Partner Relationships (parent/child linking) and authorization cascade

Understanding the Relationship Model

Organization BP (parent)
  └── to_BusinessPartnerChildren
       ├── John Smith   → relationshipType: CEO (15)
       ├── Jane Doe     → relationshipType: CFO (16)
       ├── Bob Trader   → relationshipType: Trader (02)
       └── Carol Admin  → relationshipType: Client Admin (19)

Natural Person BP (child)
  └── to_BusinessPartnerParents
       └── ACME Corporation  → relationshipType: CEO (15)

The relationship is bi-directional: viewable from both the parent’s Children table and the child’s Parents table.

Key Relationship Types and Their Authorization Effects

CodeAreaNameAuthorization Impact on the Child
19SFClient AdminCan UPDATE the parent Organization BP
27SFPartner ManagerCan READ the parent Organization BP
29TDDeals ManagerCan CREATE, READ, UPDATE deals for the org
30TDDeals ViewerCan READ deals for the org
28TDOn Behalf OfCan trade on behalf of the org
02SFTraderRole designation — used in deal workflows
03SFApproverRole designation — used in approval workflows
01LGContactInformational — no special authorization
07LGCompliance OfficerRole designation
15LGCEORole designation
16LGCFORole designation
14LGShare HolderInformational — use ownershipPercentage field

Step 3.9 — Test Authorization (Client Login)

This is where you test that the relationship actually grants access:

  1. Open a private/incognito browser window
  2. Go to the Work Zone launchpad URL
  3. Log in as the IAS user Carol Admin (or whichever test user you linked as Client Admin)
    • This user must have only the Client role in XSUAA (not Treasury)
  4. Navigate to the Business Partners app
  5. Try to view and edit ACME Corporation’s BP record
Expected for Client Admin (code 19)Result
Can see ACME Corporation in listYes
Can open ACME’s Object PageYes
Can click Edit and modify fieldsYes
Can see other orgs not linked to themNo (filtered)

If the user cannot see or edit the org, check:

  • The relationship isActive = true
  • The relationship’s child_ID matches the user’s iasUserId (which = their BP ID)
  • The user has the Client role in XSUAA

Step 3.10 — Test Partner Manager (Read-Only Access)

Add a Partner Manager (code 27) relationship for another user and verify they can READ but not UPDATE the org BP.

BTP Troubleshooting

IssueWhat to Check
IAS User Management shows no userscua-ias destination configured in BTP Destination Service? IAS trust established? Check cf logs kompas-srv --recent for SCIM API errors
Refresh Data fails with errorIAS SCIM API credentials in cua-ias destination may be expired. Check destination configuration
Claim User says “BusinessPartner already exists”User was previously claimed. Check hasPartner flag — if true, the BP already exists
Onboard Client failsIAS group “Kompas Client” must exist in the IAS tenant. Check cf logs kompas-srv --recent
Revoke Access does not immediately block userXSUAA tokens are cached (typically 30 min). User retains access until token expiry
Client user cannot see organization BPRelationship must be isActive = true, child_ID must match the user’s IAS user ID (which equals their BP ID), and the user must have the Client role
Client Admin cannot edit organization BPRelationship type must be 19 (Client Admin). Types 27 (Partner Manager) or 01 (Contact) only grant READ, not UPDATE
Cannot save BusinessPartnershortCode must be exactly 4 chars matching [A-Z0-9]{4}. Check all mandatory fields are filled
Organization name field missingEnsure businessPartnerCategory_code = "01" (Organization — code 01 in this system). If Natural Person (02), the org name field won’t appear
Sub-tables (Addresses, Banks, etc.) don’t saveEach composition must be added via the + button in its own table toolbar, not on the main form
403 Forbidden on any actionYour user does not have the required XSUAA role. Check role collection assignments in BTP cockpit → Security → Role Collections
500 Internal Server ErrorCheck backend logs: cf logs kompas-srv --recent. Likely PostgreSQL constraint violation or IAS API failure
